# edup-client

Клиент IPv4-туннеля для Linux и Windows: TUN через `tun-rs`, два потока
передачи, обфускация из `edup-common`, KEEPALIVE и MSS clamping.

## Сборка и запуск

Из корня workspace:

```sh
cargo build --locked --release -p edup-client
```

Скопируйте `config/client.example.toml` в `client.toml`. Задайте IPv4-адрес
и UDP-порт сервера, пароль и ID пользователя, включённого в конфигурацию
сервера. `tunnel_net` должен совпадать с сервером; адрес клиента вычисляется
как адрес сети плюс ID. DNS-имя в `server` не поддерживается.

Linux: нужны `/dev/net/tun`, `iproute2` и права root.

```sh
./target/release/edup-client --config client.toml check
sudo ./target/release/edup-client --config client.toml run
```

Windows: положите `wintun.dll` соответствующей архитектуры из официального
дистрибутива [Wintun](https://www.wintun.net/) рядом с `edup-client.exe`.
Можно задать абсолютный путь в `wintun_dll` (в TOML удобно использовать
одинарные кавычки: `wintun_dll = 'C:\edup\wintun.dll'`).
Запускайте `run` из PowerShell от администратора:

```powershell
.\target\release\edup-client.exe --config client.toml check
.\target\release\edup-client.exe --config client.toml run
```

`check` проверяет конфигурацию без создания адаптера, установки маршрутов
или загрузки DLL. Для Windows используются PowerShell-команды модулей
NetTCPIP и NetAdapter. Конфигурация не выводит пароль даже при ошибке TOML.

Остановка: Ctrl+C; Linux также SIGTERM/SIGHUP. После остановки выводятся
счётчики DATA, отброшенных пакетов и KEEPALIVE. Сообщение `client ready`
означает готовность локального интерфейса, а не подтверждение связи с сервером.

## Маршруты и жизненный цикл

При `routes = true` клиент сначала определяет маршрут к серверу и привязывает
UDP-сокет к исходному IPv4-адресу. Затем создаёт TUN с адресом `/32`, сохраняет
маршрут к серверу через исходный интерфейс/шлюз отдельным `/32` и добавляет
`0.0.0.0/1`, `128.0.0.0/1` через TUN. Исходный default route сохраняется.
Существующий `/32` сервера используется без изменения.

Более специфичные маршруты, включая подключённые LAN-сети, продолжают
действовать. DNS-настройки и IPv6-маршруты не меняются; это IPv4-туннель,
а не изоляция всего трафика компьютера. Linux поддерживает автоматическую
настройку в основной таблице маршрутизации; сложные policy-routing схемы
нужно настраивать самостоятельно с `routes = false`.

Имя интерфейса должно быть свободно. При существующих маршрутах `/1`
автоматическая настройка завершается ошибкой. Созданные маршруты имеют
метрику `42760`; клиент удаляет их в обратном порядке при ошибке запуска
и штатном завершении. В Windows маршруты создаются только в ActiveStore.
При `routes = false` создаётся TUN, а маршруты настраивает оператор.

SIGKILL, принудительное завершение процесса или выключение питания не
позволяют выполнить откат: маршрут `/32` через физический интерфейс может
остаться. Перед повторным запуском проверьте маршруты с метрикой `42760`;
удаляйте только относящиеся к этому клиенту записи. Смена физической сети
или её исходного адреса требует перезапуска клиента.

## Пакеты и MTU

- Поддерживаются TCP, UDP и исходящий ICMP echo с ответами, без фрагментов.
- MTU по умолчанию — `1464`: внешний IPv4/UDP и заголовок edup занимают 36 байт.
  MTU клиента должен быть не больше MTU пути минус 36 и `max_frame` сервера
  минус 36. Допустимый диапазон конфигурации — 576–1532.
- MSS в существующей TCP-опции SYN/SYN-ACK уменьшается до `mtu - 40`;
  опция не добавляется и меньшее значение не увеличивается. Контрольная
  сумма обновляется с учётом невыровненных TCP options.
- Проверяются границы заголовков, тип, flags, user, длина и внутренний адрес.
  Обфускация не обеспечивает криптографическую аутентификацию.
- KEEPALIVE отправляется сразу и далее каждые `keepalive_secs` (1–60 секунд,
  по умолчанию 15) из того же UDP-сокета. Ответы обрабатываются отдельно от DATA.
  Временные сетевые ошибки не завершают клиент; KEEPALIVE продолжается.
- GSO/GRO/USO/URO и несколько очередей пока не реализованы.

## Проверки

```sh
cargo test --locked -p edup-client
cargo clippy --locked -p edup-client --all-targets -- -D warnings
sh scripts/check-client.sh
```

Последняя команда предназначена для Linux: нужны `unshare`, `mount`, `ip`,
`ping`, `/dev/net/tun` и root либо sudo. Тест работает в отдельных mount/network
namespaces с veth и UDP echo-peer: проверяет реальный TUN, ping, UDP payload
1400 байт, KEEPALIVE, неверные ответы, маршруты, сохранение чужого `/32`,
отказ при конфликтующем `/1` и очистку по SIGTERM. Сеть хоста не меняется.
Также проверяются занятое имя адаптера и откат при частичной установке маршрутов.
Это тест клиента с эмулятором сервера; полный стенд клиент + XDP и iperf3
остаётся отдельным этапом.

На 2026-09-27: unit-тесты, Clippy и release-сборки проверены на Windows и Linux;
Linux lifecycle-тест прошёл в WSL. Также проверены ICMP, UDP DNS и TCP/TLS
через настоящий XDP-сервер на VPS; для пути с MTU 1280 использован MTU клиента
1200. На Windows проверено создание и удаление настоящего Wintun с IPv4 MTU
1200: для этого применяется `mtu_v4`, поскольку общий `mtu` в `tun-rs`
меняет также IPv6 MTU и вызывает Windows error 87 при значениях ниже 1280.
Проверена передача Windows → VPS с отдельными `/32` маршрутами: ICMP, HTTPS,
загрузка 10 МБ и получение списка серверов Speedtest. Полный автоматический
Windows lifecycle-тест маршрутов `/1` и Ctrl+C пока не выполнен.
Готовая конфигурация и пошаговый гайд описаны в [docs/WINDOWS.md](../docs/WINDOWS.md).

Регрессионная проверка Wintun из PowerShell администратора (без маршрутов `/1`):

```powershell
$env:EDUP_TEST_WINTUN_DLL = 'C:\projects\edup\local\windows-client\wintun.dll'
cargo test --locked -p edup-client windows_tests::ipv4_mtu_below_ipv6_minimum -- --ignored --exact
```

Производительность Windows: перед ожиданием уведомления сначала читается очередь
Wintun через `try_recv`. В `tun-rs 2.8.11` путь `recv_intr_timeout` ожидает событие
до чтения и может оставить пачку TCP ACK в очереди. Регрессия с настоящим Wintun
и двумя пачками по 32 UDP-пакета воспроизводит зависание старого пути и проверяет
новый; тест создаёт временный `/32` к TEST-NET и удаляет его при завершении:

```powershell
cargo test --locked -p edup-client windows_tests::queued_wintun_bursts_are_drained -- --ignored --exact
```

UDP-сокет запрашивает 4 МиБ входного и 1 МиБ выходного буфера; Linux может
ограничивать размеры через sysctl. `EDUP_DIAGNOSTICS=1` включает вывод счётчиков
каждые 5 секунд. Для Windows-пути к настроенному VPS проверен MTU 1400;
MTU 1200 не подходит для QUIC Initial (нужно минимум 1228 для IPv4/UDP).
